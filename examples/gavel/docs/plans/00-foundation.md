# 00 — Foundation: architecture, shared model, build order

Source: [use-cases.md](../use-cases.md) (v2, web-first). Every UC plan in this folder assumes the decisions below. Read this one first.

## 1. Deliverable

One Serverpod server that also serves a Flutter **web** build. The join link (`https://<host>/a/<CODE>`) is the whole funnel. There's no native build for the MVP; native is roadmap (`flutter build apk` from the same app).

## 2. Package layout

```
examples/gavel/
  docs/                      use cases + these plans
  gavel_server/              Serverpod 4.0.4 server (domain + endpoints + read models)
    lib/src/domain/          pure Dart: aggregates, events, commands, errors, saga (no serverpod imports)
    lib/src/infra/           repositories, table projections, live notifier glue
    lib/src/endpoints/       AuctionEndpoint, LotEndpoint, LiveEndpoint
    lib/src/future_calls/    TaroDomainCalls, AuctionCloseCalls
    lib/src/models/          *.spy.yaml read models + DTOs
    web/app/                 output of `flutter build web` (copied by script)
    test/                    domain unit tests (tarodomain_local) + integration (serverpod_test)
  gavel_client/              generated by `serverpod generate` — never edit
  gavel_flutter/             Flutter web app
```

- Add `gavel_server` and `gavel_client` to the root `pubspec.yaml` `workspace:` list, like `bank_account_serverpod`.
- `gavel_flutter`: try adding it to the workspace too (needs `flutter pub get` at the root to resolve). If that fights with the Dart-only melos scripts, keep it outside the workspace with `path:` dependencies on `gavel_client`. Decide within the first 30 min and don't revisit.
- The domain stays in `gavel_server/lib/src/domain` (no separate `gavel_domain` package) to save time. It must not import `serverpod` so that unit tests run on `tarodomain_local`, which is fast.

## 3. Server stack

- Copy the shape of `examples/bank_account_serverpod`: `TaroDomainServerpod(definition, scheduleCatchUp: …)..install()`, `validate(pod)` after start, and recurring `catchUp`/`sagaTimeouts`/`cleanup` jobs.
- **Database:** use SQLite for dev and the demo (as the bank example does), which keeps hosting to a single process. Switch to Postgres only if the hosting target needs it. Both work because everything goes through the ORM.
- **Default consistency: `ConsistencyMode.strong`** for every command (see use-cases §5). Projections then update in the command's transaction, so the read model and the live push are never ahead of or behind the event store.
- Snapshots: `snapshotEvery(100)`. A lot gets about 50 bids, so this hardly matters.

### Aggregates

| Aggregate | Kind | Stream / table | Owns |
|---|---|---|---|
| `Auction` | event-sourced | `Auction-<uuid>` | title, code, closeAt, organizerKeyHash, lotIds, status OPEN → CLOSING → CLOSED |
| `Lot` | event-sourced | `Lot-<uuid>` | ladder, closeAt (copied), bids[], status OPEN → SOLD/PASSED |
| `Participant` | **state-based** (`ServerpodStateRepository`) | `gavel_participants` row | auctionId, displayName |

### Events (payloads extend use-cases §6 where noted)

| Event | Aggregate | Payload |
|---|---|---|
| `AuctionCreated` | Auction | auctionId, code, title, closeAt (UTC ISO), organizerKeyHash |
| `LotRegistered` | Auction | lotId — *added*, so the close saga knows the lots without reading a projection |
| `AuctionClosed` | Auction | lotIds, cause (`DEADLINE`) |
| `AuctionFinalized` | Auction | — (saga's completion marker) |
| `LotCreated` | Lot | lotId, auctionId, name, openBid, increments[], description, imageUrl?, tileEmoji, tileColor, closeAt, position |
| `ParticipantJoined` | Participant | participantId, auctionId, displayName |
| `BidPlaced` | Lot | participantId, **bidderName** (denormalized for `leaderName`), amount, sequence |
| `BidRetracted` | Lot | participantId, retractedSequence |
| `LotClosed` | Lot | outcome (SOLD/PASSED), winnerId?, winnerName?, finalPrice?, cause (DEADLINE/SELL_NOW), closedAt |

### Commands

`CreateAuction`, `AddLot`, `JoinAuction`, `PlaceBid`, `RetractBid`, `CloseAuction`, `CloseLot(cause)`, `FinalizeAuction`. Each UC plan says which handler owns which.

### Typed errors

All live in `domain/errors.dart` as `final class … extends DomainError` with a stable `code` and a JSON-safe `context`:

| Error | code | context |
|---|---|---|
| `OutbidError` | `OUTBID` | currentPrice, leaderName, leaderId, version |
| `LotClosedError` | `LOT_CLOSED` | closedAt |
| `InvalidIncrementError` | `INVALID_INCREMENT` | allowedIncrements, currentPrice |
| `RetractNotAllowedError` | `RETRACT_NOT_ALLOWED` | reason (`NOT_LATEST`, `NOT_OWNER`, `NO_BIDS`) |
| `AuctionNotFoundError` | `AUCTION_NOT_FOUND` | code |
| `NotOrganizerError` | `NOT_ORGANIZER` | — *added* (organizer key mismatch) |
| `NotParticipantError` | `NOT_PARTICIPANT` | — *added* (unknown participant, wrong auction, or participant key mismatch) |
| `CommandValidationError` (framework) | `COMMAND_VALIDATION` | field, reason |

`TaroDomainServerpod.dispatch` already converts a `FrameworkError` into `TaroDomainException(code, context JSON)`. Read-only endpoints that throw domain errors themselves wrap the call in `rethrowAsTaroDomainException`.

**Client side:** `gavel_flutter/lib/core/failures.dart` turns a `TaroDomainException` into a sealed `GavelFailure` (`Outbid`, `LotClosed`, `InvalidIncrement`, …) by parsing `code` + `jsonDecode(context)`. The UI switches on that type and never on message strings.

### Read models (Serverpod tables, written by projections)

| Table | Model | Written by | Used by |
|---|---|---|---|
| `gavel_auctions` | `AuctionView` | `AuctionTableProjection` | UC-01/03/04/08/11 |
| `gavel_lot_cards` | `LotCard` | `LotTableProjection` | UC-04/05/09/11 |
| `gavel_ledger_entries` | `LedgerEntry` | `LotTableProjection` | UC-05/07/09 |
| `gavel_participants` | `ParticipantRow` (serverOnly) | `ParticipantRepository` (state) | UC-03 |

`LotCard` includes `version` (the lot aggregate version), which the client sends back as `expectedVersion`.

### Live channel (UC-12)

- Channel name: `auction:<CODE>`.
- Message: `LiveUpdate { kind: LOT_CHANGED | AUCTION_CHANGED, lot: LotCard?, ledgerEntry: LedgerEntry?, auction: AuctionView? }`.
- Projections post through `LiveProjectionNotifier(session).post(...)`, which sends after commit only.
- `LiveEndpoint.watch(session, code)` returns `session.messages.createStream<LiveUpdate>('auction:$code')`.

## 4. Identity & organizer guard (no auth)

- **Bidder:** `join` returns a `participantKey` (32 random bytes, base64url) next to the `participantId`. The server stores only its SHA-256 in `ParticipantRow.keyHash`. The client keeps `localStorage['gavel:<CODE>'] = {participantId, participantKey, displayName}` (UC-03).
  - `participantId` is public: it appears in `LotCard.leaderId` and `LedgerEntry.participantId`. On its own it proves nothing.
  - Every bidder action (`placeBid`, `retractBid`, `checkParticipant`) takes `participantId` **and** `participantKey`. The endpoint helper `_verifyParticipant(session, auctionId, participantId, key)` loads the row and compares hashes in constant time. On an unknown ID, a different auction or a wrong key, it throws `NotParticipantError` and nothing is dispatched.
  - The key never goes into a command, event or log. Commands carry only the verified `participantId`.
  - Clearing browser storage loses the identity: the bidder joins again as a new participant. Existing bids stay with the old ID, and that bidder can no longer retract them. That's accepted for the MVP.
- **Organizer:** `CreateAuction` returns an `organizerKey` (random 128-bit, base64url). The server stores only its SHA-256 in `AuctionCreated`. The client keeps it in `localStorage['gavel:<CODE>:org']`. `AddLot` and `SellNow` require it and throw `NotOrganizerError` on a mismatch. This is the minimum needed to stop a bidder from adding lots, and it isn't real auth.

## 5. Time

- Store everything in UTC. Display in the browser's local zone (`DateTime.toLocal()`), which is WITA for the demo.
- **Clock skew:** every board fetch returns `serverNow`. The client keeps `offset = serverNow - DateTime.now()` and drives every countdown from `now + offset`, because phones can be off by tens of seconds.
- **The deadline is enforced by the domain and not only by the scheduler.** `Lot` carries `closeAt`. `PlaceBid`/`RetractBid` with `command.timestamp >= closeAt` throws `LotClosedError` even if the close call hasn't fired yet. That makes UC-06 3c deterministic.

## 6. Flutter web app

- Packages: `gavel_client`, `serverpod_flutter`, `go_router`, `shared_preferences` (localStorage on web), `intl` (`NumberFormat.currency(locale: 'id_ID', symbol: 'Rp ', decimalDigits: 0)` → `Rp 250.000`), `flutter_web_plugins` (`usePathUrlStrategy()`).
- State: plain `ChangeNotifier` controllers (`AuctionController`, `LotController`), with no Riverpod or Bloc, to keep the time budget.
- Routes:
  - `/` home (create auction or enter a code)
  - `/a/:code` board (join prompt if no identity)
  - `/a/:code/lot/:lotId` lot detail
  - `/a/:code/organizer` dashboard
  - `/a/:code?screen=board` big screen
- Layout: single column under 600 px and a grid above it. Chips sit in a bottom bar on phones so the thumb can reach them.
- **Serving:** `flutter build web --release` → copy `build/web` to `gavel_server/web/app`. Serve it from Serverpod's web server with a static route plus an **SPA fallback to `index.html`** for `/a/*`. Check the exact route class (`StaticRoute` / `FlutterRoute` / `RouteStaticDirectory`) in Serverpod 4.0.4 during the foundation step. If deep-link fallback fights back, switch to the hash URL strategy (`/#/a/CODE`), because Facebook's link wrapper keeps fragments.
- Client URL: `Client(Uri.base.origin + '/api/')` or whatever port mapping the hosting uses. Keep it in one `config.dart`.

## 7. Testing strategy

- **Domain unit tests** (`test/domain/`) on `tarodomain_local`: every invariant and every typed error, including the bid/close race. These are cheap, so write them first for each UC.
- **Integration tests** (`test/integration/`, `serverpod_test`): one happy path per endpoint, plus the concurrency test for UC-06 (two parallel `placeBid` calls with the same `expectedVersion` give exactly one success and one `OUTBID`).
- **Manual web check** for each UC: two browser windows, one of them incognito.

## 9. Foundation step checklist (step 0)

1. `serverpod create gavel` (or copy the bank example skeleton) into `examples/gavel/`, then rename to `gavel_server` / `gavel_client`.
2. Add the dependencies `tarodomain`, `tarodomain_serverpod_server`, and `tarodomain_testing` (dev), and register the TaroDomain module in `config/generator.yaml` as the bank example does.
3. `gavel_flutter`: `flutter create --platforms=web gavel_flutter`, then add the dependencies above.
4. `TaroDomainCalls extends TaroDomainFutureCall {}` plus `scheduleTaroDomainJobs` copied from the bank example.
5. Empty `gavelServerDefinition()` builder, plus `validate()` at start-up.
6. Script `tool/build_web.sh`: `flutter build web` → rsync to `gavel_server/web/app`.
7. Smoke test: open `http://localhost:8082/a/TEST` and see the Flutter app with `TEST` parsed from the URL.
